# Diagram text alternatives and captions

These seven diagrams are original book illustrations. Their practice sequences and example evidence are editorial guidance, not empirical results or a validated assessment. Keep the companion explanation near the figure, and retain each SVG's embedded title and description.

## capability-ladder.svg

**Short alt:** Six SSA-CMM levels rise from Task Operator to Sovereign Architect, with this book's example evidence for each level.

**Caption:** TFIS level names paired with this book's practice evidence. Demonstrated capability is specific to a domain; finishing chapters does not establish a level or confer certification.

**Full explanation:** Read upward from L0 Task Operator, through L1 AI-Assisted Operator, L2 Workflow Orchestrator, L3 Agent Supervisor, and L4 Multi-Agent Architect, to L5 Sovereign Architect. The book's example evidence is, respectively, a checked manual result; an independently verified assisted result; a repeatable and measured workflow; bounded agent runs with reviewed failures; coordination that justifies its added cost; and a system the owner can restore, move, and sustain. These are practice examples for using TFIS's model, not an official scoring rubric or validated certification. The diagram uses the TFIS homepage labels; the book's source note should explain any label differences in the other TFIS assets.

**Source treatment:** Cite the verified TFIS homepage SSA-CMM source for the level names in the chapter caption or surrounding paragraph. Identify the evidence examples as this book's original operationalization; do not attribute them to an empirical study.

## curiosity-loop.svg

**Short alt:** A clockwise loop connects question, investigate, explain, test, apply, and review; review produces a new question.

**Caption:** Curiosity compounds when a pass produces checked understanding, a useful artifact, and a more precise next question.

**Full explanation:** Name an uncertainty before investigating it. Find relevant sources and check what those sources cannot establish. Explain the idea in your own words. Design a test that could reveal a mistake, then apply what survives to useful work. Review how the result compares with the expectation. That review generates the next question. Preserve a short record of what changed and the evidence behind the change so the next pass builds on experience rather than repeating it. The numbered sequence shows a complete pass, not a claim that every real project proceeds without returning to earlier steps.

## memory-lanes.svg

**Short alt:** Working context moves into a project workspace; a human review boundary precedes durable memory and a portable archive.

**Caption:** Promotion into durable memory is a decision. Preserve useful, reviewed knowledge with its evidence and conditions of use.

**Full explanation:** Working context holds the current task and immediate constraints. A project workspace retains the files, drafts, decisions, sources, and run records needed for that project. Before promotion into reviewed durable memory, check the item's source, relevance, sensitivity, and useful scope. Failed review means revision or disposal, not silent promotion. Reviewed durable memory stores reusable knowledge with evidence and a review date. A portable archive packages exported files, provenance, versions, and restore notes so the owner can recover and move the system. These lanes have different purposes and retention needs; the diagram is not a recommendation to preserve all information permanently. The downward route is the illustrated promotion/export path, while the rust return path shows revision after review.

## verified-learning-loop.svg

**Short alt:** Delegation leads to bounded execution and a human verdict; verified findings enter memory, and the next run reads the verdict. Failure escalates.

**Caption:** A run becomes reusable learning after its result is checked, the verdict is recorded, and the next run actually reads that verdict.

**Full explanation:** Begin with a delegation that states the intended result, scope, acceptance criteria, limits, permissions, and stop conditions. Bounded execution returns an artifact and a run record. A human compares them with the criteria and records what passed, what failed, and why. Only verified findings are promoted into memory, together with evidence, scope, limits, and a review date. The next run reads the verdict before updating its delegation. Failure or uncertainty follows the dashed rust route to escalation, where a human revises the scope or stops the work. An explanation of failure may itself become a useful verified lesson, but unsupported output is not promoted merely because it was generated. The main pine return path shows reuse of a reviewed lesson; the rust path shows intervention after failure or uncertainty.

## System contracts

A coordinator joins a candidate with expectations derived from the source. The comparison identifies the exact candidate version it inspected. A missing report, duplicate artifact role, or stale target prevents a complete packet. Compatible returns go to human review; they do not create the verdict themselves. One reader can rehearse these roles sequentially.

## Enterprise operations

The proposed service moves from intake and scope through evidence preparation, internal drafting and checking, review of the complete deliverable, authorized delivery, and support. Memory, capacity, maintenance, and recovery support the whole route. The figure maps prospective responsibilities; it does not depict an already validated business.

## Value and capacity

Both monthly scenarios assume 160 available owner hours, forty fixed operating hours, USD 200 fixed cash, and USD 50 per owner hour. The seven-hour baseline permits seventeen units and 159 total owner hours. At USD 300 per unit and USD 20 variable cash, it leaves USD 4,560 before the owner allowance and tax, then negative USD 3,390 after the allowance. The proposed six-hour unit permits twenty units and 160 total hours. At USD 750 and USD 35 variable cash, it leaves USD 14,100 before the allowance and USD 6,100 afterward. Capacity is not demand, and the allowance is not proof of a paid wage. Prices, volumes, costs, cash timing, and efficiency remain assumptions.
